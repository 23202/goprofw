# 07 · 待验证清单

按"信息量 / 风险"排序，前面的做完再决定后面的。

## 无风险（只读）

- [ ] 用 `ispterm` 连 RTOS，dump：sensor 型号、当前能力表、支持的 (res,fps,fov) 组合
- [ ] `gpltcmd` 列出测试套件，找 video / res / fps 相关
- [ ] 手动切到 8K，抓 `gplogd` 日志，记录 RTOS 返回的错误码
- [ ] 读 `CSI_MODEL_NUMBER` / `CSI_MODEL_NAME`，确认手头机器是 5 个机型里的哪一个
- [ ] 对比 A/B 两台机器的实际拍摄能力（视场角、最低照度、最高帧率）判断 sensor 是否同源

## 低风险（可回退）

- [ ] SD `arm-ep/` 覆盖 `settings.json`，看界面是否出现 8K60
- [ ] 修改后观察是否只是"界面有、录制回落 30p"

## 中风险

- [ ] 改 `cammodel`（记下原值），看能力表是否随型号变化
- [ ] 若变化：说明 RTOS 按型号分档，接着判断硬件是否匹配

## 高风险（需要 recovery 保障）

- [ ] 确认 fwupdate 是"先整包校验再写"还是"边写边校验"
- [ ] 串口 + 混合包，观察失败发生在哪一层（容器验签 / p2 解密 / RTOS 硬件自检）

## 待补充的数据

- [ ] 另一台机器的 `DATA.bin`（已有 B 包，若还有第三个版本可做三方对比）
- [ ] `mfg.json` 原文（`cammodel`、`boardname`、`camerasn`）
- [ ] RTOS 启动日志（串口或 `gplogd`）
- [ ] `ispterm` 的完整菜单输出

## 已知未解问题

1. 96B 签名块是不是 ECDSA P-384？签名覆盖范围是什么？
2. 16B tag 是什么（MAC？签名分量？）——已排除简单摘要。
3. 容器头签名是否覆盖全包内容（决定混合包可行性）。
4. p1 里那 64B 签名的用途。
5. 5 个机型对应的市场名称（64 是 360° 双镜头，65 是 8K/8K 4:3 那台）。
